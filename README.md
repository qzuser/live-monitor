# live-monitor 直播开播 / UP主稿件监控插件

基于 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 的监控插件：在聊天里添加要监控的**直播间**和 **B站 UP 主**，自动检测开播/关播、UP 主新稿件，并推送通知给订阅的群或个人。

## 功能特点

- 直播间监控支持平台：**B站直播、斗鱼、虎牙、抖音直播**
- **B站 UP 主新稿件监控**：用 `/直播监控 监控UP <mid 或 空间链接>` 添加 UP 主，检测到新视频就推送**标题、BV号、发布时间、视频链接与稿件封面**
- 聊天内指令管理监控列表，无需改配置文件
- 开播 / 关播自动推送通知，富文本模板包含**通知类型、主播名、平台、房间号、直播标题、直播间链接、直播封面图**
- 通知白名单（`notify_whitelist`）：按会话 UMO 精确控制哪些群/私聊实际接收推送（开播、关播、稿件通知都受它约束）
- **稿件检查间隔独立可配**（`upload_check_interval`，默认 300 秒）：稿件变化不像开播那样频繁，单独用低频轮询，不占用直播接口配额
- **首轮只记基线**：刚添加的 UP 主只记录当前已有稿件，不会把历史视频补推送一遍；重启/重载后同理，不刷屏
- **批量补档合并推送**：一次检查发现多条新稿件时按 `upload_max_notify`（默认 3）条数出详情，多余的合并成一条列表消息
- **支持热重载**：WebUI 重载/停用插件时自动保存数据、停止旧轮询任务；重复重载不会产生双任务并发推送；配置项（间隔、白名单、管理员等）修改即时生效，无需重启
- 管理员机制：可在配置中设置 `admin_ids`，仅管理员可添加/删除/订阅（留空则所有人可用）
- **开播/关播检测间隔分开自定义**：未开播房间高频轮询等开播，直播中房间低频轮询等关播，互不干扰
- 谁添加谁订阅，通知会推送给所有订阅的会话（群聊、私聊均可）
- **多群广播可靠投递**：封面图整次通知只下载一次并转 base64 复用（每群各发一条独立消息链，群与群之间间隔 1 秒），避免 AstrBot 每次发送都重新拉图被 CDN 防盗链拦截、导致除第一个群外整条通知丢失；带图发送失败会自动退回纯文字补发
- 监控与订阅数据持久化到磁盘，**机器人重启 / 插件重载后不丢失**，且重启后首次检测只记录状态、不刷屏
- 单个房间 / 单个 UP 主接口失败不影响其他监控（连续失败会写入日志）
- **插件自动检查新版本**：后台按间隔（默认 24 小时）查一次 GitHub Release，发现正式版新版本就把更新提醒发给所有订阅过通知的会话，同一版本只提醒一次；管理员也可随时用 `/直播监控 检查更新` 手动查

## 安装

1. 下载本仓库，或下载 Release 页的 `live_monitor_v<版本>.zip`
2. 把 `main.py`、`metadata.yaml`、`_conf_schema.json` 放进 AstrBot 的 `data/plugins/live_monitor/`（目录名用 `metadata.yaml` 里的 `name`，AstrBot 按它生成模块路径 `data.plugins.live_monitor.main`）：

   ```
   data/plugins/live_monitor/
   ├── main.py
   ├── metadata.yaml
   └── _conf_schema.json
   ```

3. 在 AstrBot WebUI「插件管理」中重载插件并启用即可。

> 从旧版本升级只需覆盖 `main.py`（`metadata.yaml`、`_conf_schema.json` 有新增配置项时一并覆盖）；监控数据在 `data/plugin_data/live_monitor/rooms.json`，不会被更新动到。
>
> **升级到 0.2.0 后请在 WebUI 里重载一次插件**：0.1.2 的 `投稿 / 投稿列表 / 投稿通过 / 投稿拒绝 / 审核订阅 / 审核取消` 已整套移除，旧进程不重载的话这些指令还会残留。

> 依赖 `aiohttp`，AstrBot 已内置，无需额外安装。
>
> 命名与规范注意（依据官方开发文档 <https://docs.astrbot.app/dev/star/plugin-new.html> 与 AstrBot 源码）：
> - `metadata.yaml` 的 `name` 必须是合法 Python 标识符（下划线，不能含 `-`），本插件为 `live_monitor`；
> - 插件主类名必须以 `Plugin` 结尾（本插件为 `LiveMonitorPlugin`），否则 AstrBot 扫描不到；
> - `astrbot_version` 使用 PEP 440 范围且不加 `v` 前缀；
> - 代码用 `ruff format` 格式化；依赖用 `aiohttp`（AstrBot 已内置 `aiohttp>=3.11.18`，因此本插件不提供 `requirements.txt`，避免重载时多余的 pip 步骤）；
> - **插件类里不要定义 `__del__`**：AstrBot 的 `_terminate_plugin()` 是 `if "__del__" ... elif "terminate" ...`，一旦有了 `__del__`，`terminate()` 就不会被调用，后台轮询任务不会被取消，重载后会出现双任务并发推送。

## 使用方法

指令前缀：`/直播监控`（别名 `/开播监控`）

### 直播间

| 指令 | 说明 | 权限 |
| --- | --- | --- |
| `/直播监控 添加 <直播间链接>` | 添加监控并订阅本会话通知 | 管理员 |
| `/直播监控 添加 <平台:房间号>` | 同上，手动指定平台 | 管理员 |
| `/直播监控 订阅 <平台:房间号>` | 本会话订阅某个已监控房间 | 管理员 |
| `/直播监控 取消 <平台:房间号>` | 取消本会话订阅（不删除监控） | 管理员 |
| `/直播监控 删除 <平台:房间号>` | 删除整个监控 | 管理员 |

### B站 UP 主新稿件

| 指令 | 说明 | 权限 |
| --- | --- | --- |
| `/直播监控 监控UP <mid>` | 添加 UP 主并订阅本会话稿件通知（先校验 mid 存在） | 管理员 |
| `/直播监控 监控UP https://space.bilibili.com/<mid>` | 同上，直接发空间链接 | 管理员 |
| `/直播监控 订阅UP <mid 或 UP主昵称>` | 本会话订阅某个已监控 UP 主的新稿件 | 管理员 |
| `/直播监控 退订UP <mid 或 UP主昵称>` | 取消本会话稿件通知（不删除监控） | 管理员 |
| `/直播监控 移除UP <mid 或 UP主昵称>` | 删除该 UP 主的稿件监控 | 管理员 |

### 通用

| 指令 | 说明 | 权限 |
| --- | --- | --- |
| `/直播监控 列表` | 查看监控的直播间与 UP 主及当前状态 | 所有人 |
| `/直播监控 检查更新` | 立即查一次 GitHub 上有没有新版插件 | 管理员 |
| `/直播监控 帮助` | 查看帮助 | 所有人 |

> 配置了 `admin_ids` 后，非管理员执行受限指令会提示"该操作仅限管理员"。

### UP 主稿件监控流程

```text
管理员: /直播监控 监控UP https://space.bilibili.com/946974
插件:  （调 card 接口校验 mid，取回昵称、头像、稿件总数）
插件:  ← "已添加UP主监控: 影视飓风（mid 946974，共 951 条稿件），本会话将收到新稿件通知。
          稿件检查间隔 300 秒，首轮只记录已有稿件作为基线，不会补推送历史视频。"
插件:  （到点查该 UP 主最新稿件列表，与已记录的 BV 号比对）
插件:  → 发现新 BV 号 → 推送给该 UP 主的所有订阅会话（每群间隔 1 秒）
```

要点：

- **mid 就是空间地址 `space.bilibili.com/` 后面的数字**，`bili:946974`、`946974` 这类写法同样接受。
- **直播间链接会被明确拒掉**：`live.bilibili.com/` 后面的数字是房间号，跟 mid 不是一回事，拿去当 mid 会监控到另一个人。插件识别到直播链接直接提示，不会偷偷解析。
- `监控UP` 会先调接口校验 mid 真的存在（查不到昵称就报 `UP主校验失败: ...`），避免把错号加进监控列表。
- 添加时只记基线，**不会补推送历史视频**；同理重启/重载后的第一次检查也只做对比，不刷屏。
- `订阅UP / 退订UP / 移除UP` 支持用 **UP 主昵称**代替 mid（先按 mid/链接解析，再按已监控的昵称精确匹配）。
- 稿件通知走的是和开播通知完全相同的投递路径：封面只下载一次转 base64、每个会话独立消息链、带图失败自动退纯文字、受 `notify_whitelist` 约束。

### 支持的添加方式示例

```text
/直播监控 添加 https://live.bilibili.com/123456        B站直播间链接
/直播监控 添加 https://space.bilibili.com/946974       B站主播主页（自动解析房间号）
/直播监控 添加 https://www.douyu.com/85894             斗鱼链接
/直播监控 添加 https://www.huya.com/房间号              虎牙链接
/直播监控 添加 https://live.douyin.com/742060668528    抖音链接
/直播监控 添加 bili:123456                             平台前缀写法
/直播监控 添加 斗鱼:85894                               中文前缀亦可（b站/斗鱼/虎牙/抖音）
/直播监控 添加 123456                                   纯数字默认按 B站房间号处理
```

`监控UP` 接受 `space.bilibili.com/<mid>`、`bili:<mid>`、纯数字 mid；直播间链接不接受。注意同一个 `space.bilibili.com/xxx` 地址在两条指令里含义不同：`添加` 会去解析这个主播的**直播间房间号**，`监控UP` 取的是**mid 本身**。

## 插件自动更新检查

插件会自己查有没有新版本，但**只提醒、不自动覆盖文件**——真正的更新动作仍然由 AstrBot 的插件管理器执行，避免插件自己改自己的目录。

- 版本号只写在 `metadata.yaml` 里一份，插件启动时读它，同时从 `repo` 字段解析出仓库地址（本插件是 `qzuser/live-monitor`）。
- 启动 60 秒后做第一次检查（避开插件加载阶段主动消息通道还没就绪），之后每 `update_check_interval_hours` 小时查一次，复用原来那一个轮询任务，不会新增后台任务。
- 查的是 `https://api.github.com/repos/<仓库>/releases`，并且**跳过 draft、prerelease 以及 tag 名带 alpha/beta/rc/dev 的版本**——口径和 AstrBot 自带更新器一致，防止提醒你的版本在 WebUI 里根本点不了更新。
- 发现新版本 → 发给**所有订阅过通知的会话**（直播间 `watchers` 与 UP 主 `watchers` 去重后的并集，再按 `notify_whitelist` 过滤），并把提醒过的版本号记下来，**同一个版本只提醒一次**（重启/热重载后会重新提醒一次）。
- 一个订阅会话都没有时不静默丢弃，日志里会写"没有订阅会话可提醒，管理员请用 /直播监控 检查更新 查看"。

提醒长这样：

```text
🆕 直播监控插件可更新
────────────────
📦 当前版本：v0.1.2
✨ 最新版本：v0.2.0
🗓 发布于：2026-11-02
🔗 https://github.com/qzuser/live-monitor/releases
────────────────
- 新增B站UP主新稿件监控
- 移除群友投稿审核
────────────────
更新方式：AstrBot WebUI → 插件管理 → 本插件 → 更新（由 AstrBot 覆盖插件目录，监控数据在 data/plugin_data 下不受影响）
```

`/直播监控 检查更新` 是同一套逻辑的手动入口：没新版本时回"当前 vX 已是最新版本（仓库最新正式版：vY）"，仓库上一个正式版 Release 都没发时回"… 上还没有正式版 Release，无法比较版本"，请求失败时回"检查更新失败: <原因>"。手动查过的版本同样会被标记，后台不会再推第二遍。

> 连不上 GitHub（网络被墙、限流 403、离线）只记一条 `检查插件更新失败: ...` 日志，**不会中断开播与稿件轮询**。彻底不想让插件联网查版本，把 `update_check` 关掉即可，之后仍然可以手动 `检查更新`。

## 配置项（WebUI 插件设置）

| 配置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `admin_ids` | string | 空 | 管理员用户ID（QQ号/Telegram ID 等），多个用逗号分隔；**留空则所有人可用**。仅管理员可执行 添加/删除/订阅/取消/监控UP/移除UP/订阅UP/退订UP/检查更新 |
| `start_check_interval` | int | 30 | **开播检测间隔**（秒）：未开播的房间按此频率轮询，检测是否开播。最小生效 15 秒，过小可能被平台限流 |
| `end_check_interval` | int | 60 | **关播检测间隔**（秒）：正在直播中的房间按此频率轮询，检测是否关播 |
| `notify_start` | bool | true | 开播时是否推送 |
| `notify_end` | bool | true | 关播时是否推送 |
| `upload_check_interval` | int | 300 | **UP 主稿件检查间隔**（秒）：只对已添加的 B站 UP 主生效，最小生效 60 秒。UP 主发稿频率低，没必要像开播那样高频查 |
| `notify_upload` | bool | true | UP 主发新稿件时是否推送。**关掉后仍会继续记录稿件基线**，重新打开不会把关掉期间的稿件补推送 |
| `upload_max_notify` | int | 3 | 一次检查最多推送几条新稿件的详情；超出则合并成一条列表消息（填 0 或非法值按默认 3 处理，最小按 1 生效） |
| `notify_whitelist` | text | 空 | **通知白名单**：仅这些会话UMO接收推送（开播/关播/稿件通知都算），多个用逗号分隔；留空则推送给所有订阅会话。格式如 `aiocqhttp:GroupMessage:123456789`、`telegram:GroupMessage:-100123`。管理员用 `列表` 指令可查看各会话的 UMO |
| `bilibili_cookie` | string | 空 | B站 Cookie（可选，直播接口或 UP 主稿件接口失败时再填） |
| `update_check` | bool | true | 是否自动检查插件新版本（访问 `api.github.com`）。关掉后仍可用 `/直播监控 检查更新` 手动查 |
| `update_check_interval_hours` | int | 24 | 自动检查新版本的间隔（小时），最小生效 1 小时；填 0 或非法值按默认 24 处理 |

> 三项间隔均可在 WebUI 插件设置中随时修改，修改后无需重启。
> 房间开播后自动切换到关播间隔，关播后切回开播间隔，兼顾响应速度与接口压力。

> 查询自己的用户ID：向机器人发送 `/sid`（AstrBot 内置指令）即可。

## 数据存储

监控列表（房间 + UP 主）保存在 `data/plugin_data/live_monitor/rooms.json`，可直接编辑/备份。**机器人重启、插件重载后监控与订阅均自动恢复**；恢复后首次检测只同步当前状态，不会重复推送通知。结构（v3）：

```json
{
  "version": 3,
  "rooms": {
    "bilibili:123456": {
      "platform": "bilibili",
      "room_id": "123456",
      "title": "直播标题",
      "anchor": "主播昵称",
      "cover": "https://...封面图.jpg",
      "url": "https://live.bilibili.com/123456",
      "live": true,
      "watchers": { "aiocqhttp:GroupMessage:123456789": "群名片" }
    }
  },
  "ups": {
    "946974": {
      "mid": "946974",
      "platform": "bilibili",
      "name": "影视飓风",
      "face": "https://...头像.jpg",
      "archive_count": 951,
      "watchers": { "aiocqhttp:GroupMessage:123456789": "群名片" },
      "seen": ["BV1eee", "BV1ddd", "BV1ccc"]
    }
  }
}
```

`watchers` 的 key 是 AstrBot 的 `unified_msg_origin`（会话标识）；房间和 UP 主各自维护一份，所以某个群可以只订阅开播不订阅稿件，或反过来。`seen` 是该 UP 主已知的 BV 号，**从新到旧**保存，最多 `MAX_SEEN_UPLOADS = 60` 条，超出会丢弃最旧的——只影响对比窗口，不影响监控本身（只要 60 条窗口内出现新 BV 号就能发现）。`seen` 为空即代表还没建立基线，下一次检查只记录、不推送。

> **旧数据自动升级**：
> - 0.1.1 及以前的 `rooms.json` 顶层直接就是房间表，插件载入时识别并读入；
> - 0.1.2 的 v2 结构里的 `submissions` / `reviewers`（群友投稿队列与审核会话）在 0.2.0 已无对应功能，载入时**直接丢弃**并写一行日志 `已忽略旧数据里的投稿队列（submissions/reviewers）…`，房间与订阅照常保留；
> - 两种情况下次保存都会写成 v3 结构，不需要手工迁移。

手工编辑过这个文件也没关系：插件载入时会校验并修复，脏数据只会被丢弃而不会让轮询任务崩溃。

| 情况 | 处理 |
| --- | --- |
| 顶层不是对象 / 房间值不是对象 | 忽略该条并写日志 |
| `platform` 不在支持列表 | 跳过该房间 |
| 缺 `room_id` | 跳过该房间 |
| 缺 `watchers`、或 `watchers` 不是对象 | 归一化成空对象（房间继续监控，只是没人订阅） |
| 缺 `title / anchor / cover / url`、`live` 不是真假 | 补成空串 / `None`（`None` 表示首次检测只记录基线，不推送） |
| `room_id` 是数字 | 转成字符串，避免后续接口拼 URL 出错 |
| UP 主 key 不是纯数字 / 值不是对象 | 跳过该 UP 主并写日志 |
| UP 主缺 `name / face`、`archive_count` 不是数字 | 补成空串 / `0` |
| UP 主 `seen` 不是列表、含空项 | 逐项转字符串并去掉空值，超过 60 条截断 |
| `watchers` 里 key 为空 | 丢弃该条订阅 |

## 收不到稿件通知的排查

1. `/直播监控 列表` 看该 UP 主那行的 `已记录 N 条稿件` 还是 `待首次检测`。**一直是"待首次检测"**说明从没成功查过（网络、Cookie、mid 有误），日志里会有 `检查UP主 <mid> 失败(第N次): ...`。
2. 列表里 UP 主行首是 `-` 而不是 `√`，说明当前会话没订阅 → `/直播监控 订阅UP <mid 或 昵称>`。`监控UP` 只给**执行指令的那个会话**订阅，其他群要各自订阅。
3. 检查 `notify_whitelist` 是否漏了这个群的 UMO——稿件通知同样受白名单约束，被跳过的会话会写日志 `以下会话不在 notify_whitelist 内，跳过推送: [...]`。
4. 想把某个 UP 主从监控里彻底去掉，用 `移除UP`；`退订UP` 只是当前会话不再收，UP 主还在列表里。
5. 加完 UP 主后立刻发的那条提示里写了检查间隔（`稿件检查间隔 300 秒`），新稿件最多要等一个间隔才会推，不是没生效。
6. 日志里出现 `handle error: 'int' object has no attribute 'strip'` → 装的是 0.1.1 及以前的旧版。AstrBot 会把纯数字指令参数转成 `int`，旧版直接 `.strip()` 就崩了；0.1.2 起做了字符串兜底，0.2.0 覆盖 `添加/删除/订阅/取消/监控UP/移除UP/订阅UP/退订UP`，升级 `main.py` 即可。

## 收不到开播通知的排查

1. 管理员在**收不到通知的那个群**里执行 `/直播监控 列表`，管理员视角会列出每个房间的订阅 UMO。若没有该群的 `aiocqhttp:GroupMessage:群号`，说明这个群根本没订阅 → 执行 `/直播监控 订阅 平台:房间号`。
2. `添加 / 订阅 / 取消 / 删除` 默认是**管理员指令**：配置了 `admin_ids` 后，其他群里非管理员发这些指令会被拒绝（提示"该操作仅限管理员"），此时把该群群主的 QQ 号加进 `admin_ids`，或暂时留空。
3. 检查 `notify_whitelist` 是否只填了第一个群的 UMO。白名单会静默过滤其他群，被跳过的会话会写进日志：`以下会话不在 notify_whitelist 内，跳过推送: [...]`。
4. 日志里若出现 `推送通知到 xxx 失败`，`xxx` 的 UMO 就是没送到的会话：平台 ID 写错、该群已踢出机器人、或平台不支持主动消息（`qq_official`）都会在这里暴露。

## 封面图与发送容错

开播通知与稿件通知都会附带封面。AstrBot 发送 http 图片链接时**每次发送都会重新拉一次图**，且不带防盗链 Referer、不校验状态码——多群广播时第 2 个群很容易拿到 403 错误页并抛异常，把整条通知（连文字一起）带走。因此本插件自己下载封面、转 base64 复用，并做了四道校验：

| 校验 | 不满足时的行为 |
| --- | --- |
| 封面地址必须是 `http(s)://` | 不发起下载 |
| HTTP 状态码必须是 200 | 放弃封面 |
| `Content-Type` 必须以 `image/` 开头 | 放弃封面（平台限流常返回 html） |
| 体积 ≤ `MAX_COVER_BYTES`（2 MB，响应头与正文各查一次） | 放弃封面 |

以上任一情况只记录 `封面下载失败，本次仅发送文字`，**文字通知照常发出**。带图消息在某个群发送失败时，还会对该群自动退回纯文字再发一次，保证通知不丢。多条稿件合并推送的那条消息不带封面（多个封面没有意义），只有单条详情通知配图。

## 已知限制

- **抖音**：无登录态时官方接口可能返回异常，插件会跳过该房间并记录日志，不影响其他房间。
- **虎牙/B站** 等接口均为非官方公开接口，平台改版后可能失效，届时需更新 `main.py` 中对应的 `check_*` / `fetch_up_*` 函数。
- **UP 主稿件只支持 B站**。
- **稿件列表每页只取最新 20 条**（`fetch_up_uploads(limit=20)`）。UP 主在一个检查间隔内发超过 20 条时会漏掉更早的几条——正常更新节奏不可能碰到，仅批量补档/搬运号需要注意。
- **B站空间接口有风控**：`x/space/wbi/arc/search` 需要 WBI 签名且频繁返回 `-352/-403`，本插件刻意不用它，改走免 WBI、免 Cookie 的 `x/v2/medialist/resource/list` + `x/web-interface/card`。若仍被限流，日志会写 `bilibili 稿件接口返回 code=-352（…）`，此时填 `bilibili_cookie` 或调大 `upload_check_interval`。
- 稿件对比靠 BV 号集合，**UP 主把旧稿件删除后又恢复、或改成同一 BV 不会重新通知**；改标题、换封面也不会（只认新 BV 号）。
- `qqofficial`（QQ 官方 API 平台）不支持 AstrBot 主动消息，无法作为通知接收会话。
- B站直播通知中的"主播"字段在接口未返回昵称时显示 uid。
- 多群广播是**逐个发送、每个群之间间隔 1 秒**（防 QQ 频控）。订阅群数很多时，最后一个群会比第一个群晚几秒收到通知。
- **更新检查依赖 `api.github.com` 可达**：机器无法直连 GitHub（没配代理/被限流 403）时查不到新版本，插件只在日志里留一行 `检查插件更新失败: ...`，不影响监控。
- 更新提醒**只负责告诉你有新版本**，不会自己下载覆盖。用 AstrBot WebUI 的插件管理更新最稳（它会覆盖整个插件目录，手工改过的 `main.py` 会被替换，监控数据在 `data/plugin_data/` 下不受影响）。

## 开发与许可

仓库：<https://github.com/qzuser/live-monitor>，Release 页提供打包好的 `live_monitor_v<版本>.zip`，下载后覆盖 `data/plugins/live_monitor/` 里的同名文件即可。

代码见 `main.py`，按 AstrBot Star 插件规范开发（`filter.command_group` 注册指令、后台单个 `asyncio` 轮询任务同时驱动房间与 UP 主两组检查、`context.send_message` 主动推送、`StarTools.get_data_dir()` 存数据、`terminate()` 清理任务）。

离线冒烟测试（不需要 AstrBot、不联网，`tests/stubs.py` 注入 astrbot 桩模块并**强制覆盖** aiohttp 为桩实现，用假 event 与假 context 直接驱动指令函数）：

```bash
python tests/run.py                # 两套一起跑
python tests/test_monitor.py       # 直播间 + UP主稿件监控
python tests/test_update_check.py  # 更新检查
```

`test_monitor.py` 覆盖旧数据升级（v1 房间表、v2 投稿队列丢弃并留痕）、UP 主添加/查重/校验失败/直播链接拒绝、昵称与 int 参数（`监控UP/移除UP/订阅UP/退订UP` 全部按 int 传一遍）、首轮基线不推送、多条合并与 `upload_max_notify` 边界、`notify_upload` 关闭仍记基线、`seen` 上限 60、白名单过滤、封面失败退纯文字、稿件接口真实路径（记录 URL 与 Referer，断言 `media_list` 解析、`ps=20`、`-352` 抛错）、轮询中单个 UP 主失败不影响其他监控、原有开播路径不受影响；`test_update_check.py` 覆盖版本号比较、跳过预发布 Release、同一版本只提醒一次、`update_check` 开关、无订阅会话与检查失败只写日志。共 33 项用例。
