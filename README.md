# live-monitor 直播开播 / UP主稿件监控插件

基于 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 的监控插件：在聊天里添加要监控的**直播间**和 **B站 UP 主**，自动检测开播/关播、UP 主新稿件，并推送通知给订阅的群或个人；发现新版插件时，管理员发一条 `/直播监控 更新` 就能下载、校验、备份、覆盖并自动热重载。

## 功能特点

- 直播间监控支持平台：**B站直播、斗鱼、虎牙、抖音直播**
- **B站 UP 主新稿件监控**：用 `/直播监控 监控UP <mid 或 空间链接>` 添加 UP 主，检测到新视频就推送**标题、BV号、发布时间、视频链接与稿件封面**
- 聊天内指令管理监控列表，无需改配置文件
- 开播 / 关播自动推送通知，富文本模板包含**通知类型、主播名、平台、房间号、直播标题、直播间链接、直播封面图**
- **距离上次的时间**（`show_elapsed` 单独开关，默认开）：开播通知带上「距离上次直播 xx天/xx小时」，稿件通知带上「距上次更新 xx天/xx小时」，不满一天按小时显示；**取不到上一次的时间就整行省略**，不会显示空字段或 0天
- **关播统计本次直播时长**：关播通知带上「⏱ 本次时长：约3小时12分钟」（`x天x小时` / `x小时y分钟` / `y分钟`，不满一分钟写「不到1分钟」）。时长用的是**真正抓到的开播瞬间**，所以插件没见过这轮开播（升级前就在播、添加时主播已开播）时这一行自动省略，不会报一个从"我发现它"算起的假时长
- 通知白名单（`notify_whitelist`）：按会话 UMO 精确控制哪些群/私聊实际接收推送（开播、关播、稿件通知都受它约束）
- **稿件检查间隔独立可配**（`upload_check_interval`，默认 300 秒）：稿件变化不像开播那样频繁，单独用低频轮询，不占用直播接口配额
- **首轮只记基线**：刚添加的 UP 主只记录当前已有稿件，不会把历史视频补推送一遍；重启/重载后同理，不刷屏
- **批量补档合并推送**：一次检查发现多条新稿件时按 `upload_max_notify`（默认 3）条数出详情，多余的合并成一条列表消息
- **支持热重载**：WebUI 重载/停用插件时自动保存数据、停止旧轮询任务；重复重载不会产生双任务并发推送；配置项（间隔、白名单、管理员等）修改即时生效，无需重启
- **房间号严格字符校验**：`平台:房间号` 的写法和手工编辑过的 `rooms.json` 都要过校验（B站/抖音纯数字、斗鱼字母数字、虎牙可含 `-` `_`），带 `& ? / #` 或路径的输入直接拒掉——房间号会被原样拼进请求 URL，放过这些字符等于让外人改写查询串
- **B站登录 Cookie 只发给B站自己的域名**：只有 `*.bilibili.com`、`*.bilibili.cn`、`*.hdslb.com` 的请求才带 `bilibili_cookie`；封面地址来自接口也可能被手工改过，不加限制就等于把登录态转发给任意站点
- 管理员机制：可在配置中设置 `admin_ids`，仅管理员可添加/删除/订阅（留空则所有人可用）
- **开播/关播检测间隔分开自定义**：未开播房间高频轮询等开播，直播中房间低频轮询等关播，互不干扰
- 谁添加谁订阅，通知会推送给所有订阅的会话（群聊、私聊均可）
- **多群广播可靠投递**：封面图整次通知只下载一次并转 base64 复用（每群各发一条独立消息链，群与群之间间隔 1 秒），避免 AstrBot 每次发送都重新拉图被 CDN 防盗链拦截、导致除第一个群外整条通知丢失；带图发送失败会自动退回纯文字补发
- 监控与订阅数据持久化到磁盘，**机器人重启 / 插件重载后不丢失**，且重启后首次检测只记录状态、不刷屏
- **写盘是原子的**：先写 `rooms.json.tmp` 再改名覆盖，写到一半崩溃、序列化失败都不会留下半个 JSON；载入时发现文件读坏了，会把原文件**改名成 `rooms.json.bad-<时间戳>` 留底**（日志给出文件名），修好它再重载即可恢复，**不会被下一次保存悄悄覆盖**
- 单个房间 / 单个 UP 主接口失败不影响其他监控（连续失败会写入日志）；轮询单轮出现意外异常也只记一行日志并继续，**后台任务不会静默退出导致全部监控停摆**
- **插件自动检查新版本**：后台按间隔（默认 24 小时）查一次 GitHub Release，发现正式版新版本就把更新提醒发给所有订阅过通知的会话，同一版本只提醒一次；管理员也可随时用 `/直播监控 检查更新` 手动查
- **一键热更新**（`/直播监控 更新`）：管理员发一条指令，插件自己从 GitHub 下载最新版的更新包、在内存里校验通过后备份旧文件并原子覆盖，然后自动热重载插件，重载成功再回执一条确认；全程**不重启 AstrBot、不动监控数据**，失败时备份目录原样可用（详见下面「插件热更新」）

## 安装

1. 下载本仓库，或下载 Release 页的 `live_monitor_v<版本>.zip`
2. 把 `main.py`、`metadata.yaml`、`_conf_schema.json` 放进 AstrBot 的 `data/plugins/live_monitor/`（目录名用 `metadata.yaml` 里的 `name`，AstrBot 按它生成模块路径 `data.plugins.live_monitor.main`）：

   ```
   data/plugins/live_monitor/
   ├── main.py
   ├── metadata.yaml
   └── _conf_schema.json
   ```

3. 在 AstrBot WebUI「插件管理」中重载插件并启用即可。

> 从旧版本升级只需覆盖 `main.py`（`metadata.yaml`、`_conf_schema.json` 有新增配置项时一并覆盖）；监控数据在 `data/plugin_data/live_monitor/rooms.json`，不会被更新动到。
>
> **升级到 0.2.0 后请在 WebUI 里重载一次插件**：0.1.2 的 `投稿 / 投稿列表 / 投稿通过 / 投稿拒绝 / 审核订阅 / 审核取消` 已整套移除，旧进程不重载的话这些指令还会残留。

> 依赖 `aiohttp`，AstrBot 已内置，无需额外安装。
>
> 命名与规范注意（依据官方开发文档 <https://docs.astrbot.app/dev/star/plugin-new.html> 与 AstrBot 源码）：
> - `metadata.yaml` 的 `name` 必须是合法 Python 标识符（下划线，不能含 `-`），本插件为 `live_monitor`；
> - 插件主类名必须以 `Plugin` 结尾（本插件为 `LiveMonitorPlugin`），否则 AstrBot 扫描不到；
> - `astrbot_version` 使用 PEP 440 范围且不加 `v` 前缀；
> - 代码用 `ruff format` 格式化；依赖用 `aiohttp`（AstrBot 已内置 `aiohttp>=3.11.18`，因此本插件不提供 `requirements.txt`，避免重载时多余的 pip 步骤）；
> - **插件类里不要定义 `__del__`**：AstrBot 的 `_terminate_plugin()` 是 `if "__del__" ... elif "terminate" ...`，一旦有了 `__del__`，`terminate()` 就不会被调用，后台轮询任务不会被取消，重载后会出现双任务并发推送。

## 使用方法

指令前缀：`/直播监控`（别名 `/开播监控`）

### 直播间

| 指令 | 说明 | 权限 |
| --- | --- | --- |
| `/直播监控 添加 <直播间链接>` | 添加监控并订阅本会话通知 | 管理员 |
| `/直播监控 添加 <平台:房间号>` | 同上，手动指定平台 | 管理员 |
| `/直播监控 订阅 <平台:房间号>` | 本会话订阅某个已监控房间 | 管理员 |
| `/直播监控 取消 <平台:房间号>` | 取消本会话订阅（不删除监控） | 管理员 |
| `/直播监控 删除 <平台:房间号>` | 删除整个监控 | 管理员 |

### B站 UP 主新稿件

| 指令 | 说明 | 权限 |
| --- | --- | --- |
| `/直播监控 监控UP <mid>` | 添加 UP 主并订阅本会话稿件通知（先校验 mid 存在） | 管理员 |
| `/直播监控 监控UP https://space.bilibili.com/<mid>` | 同上，直接发空间链接 | 管理员 |
| `/直播监控 订阅UP <mid 或 UP主昵称>` | 本会话订阅某个已监控 UP 主的新稿件 | 管理员 |
| `/直播监控 退订UP <mid 或 UP主昵称>` | 取消本会话稿件通知（不删除监控） | 管理员 |
| `/直播监控 移除UP <mid 或 UP主昵称>` | 删除该 UP 主的稿件监控 | 管理员 |

### 通用

| 指令 | 说明 | 权限 |
| --- | --- | --- |
| `/直播监控 列表` | 查看监控的直播间与 UP 主及当前状态 | 所有人 |
| `/直播监控 检查更新` | 立即查一次 GitHub 上有没有新版插件 | 管理员 |
| `/直播监控 更新 [版本号]` | 下载更新包、校验、备份并覆盖插件文件，然后自动热重载 | 管理员 |
| `/直播监控 帮助` | 查看帮助 | 所有人 |

> 配置了 `admin_ids` 后，非管理员执行受限指令会提示"该操作仅限管理员"。

### UP 主稿件监控流程

```text
管理员: /直播监控 监控UP https://space.bilibili.com/946974
插件:  （调 card 接口校验 mid，取回昵称、头像、稿件总数）
插件:  ← "已添加UP主监控: 影视飓风（mid 946974，共 951 条稿件），本会话将收到新稿件通知。
          稿件检查间隔 300 秒，首轮只记录已有稿件作为基线，不会补推送历史视频。"
插件:  （到点查该 UP 主最新稿件列表，与已记录的 BV 号比对）
插件:  → 发现新 BV 号 → 推送给该 UP 主的所有订阅会话（每群间隔 1 秒）
```

要点：

- **mid 就是空间地址 `space.bilibili.com/` 后面的数字**，`bili:946974`、`946974` 这类写法同样接受。
- **直播间链接会被明确拒掉**：`live.bilibili.com/` 后面的数字是房间号，跟 mid 不是一回事，拿去当 mid 会监控到另一个人。插件识别到直播链接直接提示，不会偷偷解析。
- `监控UP` 会先调接口校验 mid 真的存在（查不到昵称就报 `UP主校验失败: ...`），避免把错号加进监控列表。
- 添加时只记基线，**不会补推送历史视频**；同理重启/重载后的第一次检查也只做对比，不刷屏。
- `订阅UP / 退订UP / 移除UP` 支持用 **UP 主昵称**代替 mid（先按 mid/链接解析，再按已监控的昵称精确匹配）。
- 稿件通知走的是和开播通知完全相同的投递路径：封面只下载一次转 base64、每个会话独立消息链、带图失败自动退纯文字、受 `notify_whitelist` 约束。
- 「距上次更新」是**这条新稿件与它上一条投稿的发布时间差**（同一次抓取里更旧的那条），不是距上次收到通知的时间；UP 主只有一条稿件、或接口没给发布时间时，这一行自动省略。批量合并的那条消息按**最新一条**算，写成「最新一条距上次更新」。

### 支持的添加方式示例

```text
/直播监控 添加 https://live.bilibili.com/123456        B站直播间链接
/直播监控 添加 https://space.bilibili.com/946974       B站主播主页（自动解析房间号）
/直播监控 添加 https://www.douyu.com/85894             斗鱼链接
/直播监控 添加 https://www.huya.com/房间号              虎牙链接
/直播监控 添加 https://live.douyin.com/742060668528    抖音链接
/直播监控 添加 bili:123456                             平台前缀写法
/直播监控 添加 斗鱼:85894                               中文前缀亦可（b站/斗鱼/虎牙/抖音）
/直播监控 添加 123456                                   纯数字默认按 B站房间号处理
```

`监控UP` 接受 `space.bilibili.com/<mid>`、`bili:<mid>`、纯数字 mid；直播间链接不接受。注意同一个 `space.bilibili.com/xxx` 地址在两条指令里含义不同：`添加` 会去解析这个主播的**直播间房间号**，`监控UP` 取的是**mid 本身**。

### 通知示例

开播（文本 + 直播封面图）：

```text
🔴 开播通知
────────────────
👤 主播：哔哩哔哩英雄联盟赛事
📡 平台：B站直播
🚪 房间：6
📺 标题：今天和大家聊聊新版本
⏳ 距离上次直播：3天
────────────────
🔗 https://live.bilibili.com/6
```

关播（带本次直播时长）：

```text
⚫ 关播通知
────────────────
👤 主播：哔哩哔哩英雄联盟赛事
📡 平台：B站直播
🚪 房间：6
⏱ 本次时长：约3小时12分钟
────────────────
直播已结束，下次开播再会～
```

UP 主发新稿件（文本 + 稿件封面图）：

```text
📺 投稿通知
────────────────
👤 UP：影视飓风
🎬 标题：我们拍到了想拍的东西
🔖 稿件：BV1xxxxxxx
🕒 发布：2026-11-02 18:30
⏳ 距上次更新：2天
🔗 https://www.bilibili.com/video/BV1xxxxxxx
```

一次出现多条新稿件（默认最多出 3 条详情，合并成一条消息防刷屏）：

```text
📺 投稿通知
────────────────
👤 UP：影视飓风
⏳ 最新一条距上次更新：2天
🆕 新增 5 条稿件，列出最近 3 条：
· 第三条标题（BV1ccc）
  https://www.bilibili.com/video/BV1ccc
· 第四条标题（BV1ddd）
  https://www.bilibili.com/video/BV1ddd
· 第五条标题（BV1eee）
  https://www.bilibili.com/video/BV1eee
…另有 2 条未列出
```

> 多条新稿件会**按发布时间从旧到新**列出（接口返回是从新到旧，插件倒过来），和 UP 主投稿顺序一致。`upload_max_notify` 为 1 时仍然只发一条消息：出最新那条的详情（带封面），末尾附 `另有 N 条新稿件未列出`。

> 两个 `⏳` 行都归 `show_elapsed` 管：关掉开关，或插件手里没有"上一次"的时间（新房间从没记录过在播时刻、UP 主只抓到一条稿件、接口没返回发布时间），这一行就整条不出现，通知其余部分照常。
>
> 关播通知里的 `⏱ 本次时长` 不受 `show_elapsed` 控制（它不是"距离上次"的间隔，而是这一场播了多久），只在**没抓到这轮的开播瞬间**时省略。

## 插件自动更新检查

插件会自己查有没有新版本，**默认只提醒**；要真的更新，由管理员发 `/直播监控 更新` 这条指令来触发（见下一节「插件热更新」），或者照旧用 AstrBot 的插件管理器更新。插件不会在没人下的指令时自己改自己的目录。

- 版本号只写在 `metadata.yaml` 里一份，插件启动时读它，同时从 `repo` 字段解析出仓库地址（本插件是 `qzuser/live-monitor`）。
- 启动 60 秒后做第一次检查（避开插件加载阶段主动消息通道还没就绪），之后每 `update_check_interval_hours` 小时查一次，复用原来那一个轮询任务，不会新增后台任务。
- 查的是 `https://api.github.com/repos/<仓库>/releases`，并且**跳过 draft、prerelease 以及 tag 名带 alpha/beta/rc/dev 的版本**——口径和 AstrBot 自带更新器一致，防止提醒你的版本在 WebUI 里根本点不了更新。
- 发现新版本 → 发给**所有订阅过通知的会话**（直播间 `watchers` 与 UP 主 `watchers` 去重后的并集，再按 `notify_whitelist` 过滤），并把提醒过的版本号记下来，**同一个版本只提醒一次**（重启/热重载后会重新提醒一次）。
- 一个订阅会话都没有时不静默丢弃，日志里会写"没有订阅会话可提醒，管理员请用 /直播监控 检查更新 查看"。

提醒长这样：

```text
🆕 直播监控插件可更新
────────────────
📦 当前版本：v0.2.1
✨ 最新版本：v0.3.0
🗓 发布于：2026-11-03
🔗 https://github.com/qzuser/live-monitor/releases
────────────────
- 新增一键热更新
- 关播通知带本次时长
────────────────
更新方式：管理员在群里发 /直播监控 更新 即可自动下载并热更新到 v0.3.0；也可用 AstrBot WebUI → 插件管理 → 本插件 → 更新（监控数据在 data/plugin_data 下，两种方式都不受影响）
```

`/直播监控 检查更新` 是同一套逻辑的手动入口：没新版本时回"当前 vX 已是最新版本（仓库最新正式版：vY）"，仓库上一个正式版 Release 都没发时回"… 上还没有正式版 Release，无法比较版本"，请求失败时回"检查更新失败: <原因>"。手动查过的版本同样会被标记，后台不会再推第二遍。

> 连不上 GitHub（网络被墙、限流 403、离线）只记一条 `检查插件更新失败: ...` 日志，**不会中断开播与稿件轮询**。彻底不想让插件联网查版本，把 `update_check` 关掉即可，之后仍然可以手动 `检查更新`。

## 插件热更新

`/直播监控 更新` 把「发现新版 → 下载 → 校验 → 覆盖 → 重载 → 回执」串成一条指令，管理员不用碰 WebUI、不用重启机器人。

```text
管理员: /直播监控 更新
插件:   ⏬ 正在从 https://github.com/qzuser/live-monitor 下载最新版更新包…
插件:   （查 Releases、挑更新包、下载、内存里校验）
插件:   （把旧的 main.py / metadata.yaml / _conf_schema.json / README.md 拷进备份目录，逐个原子覆盖）
插件:   ✅ 已下载 v0.3.0 并覆盖 4 个文件
        ────────────────────────
        📦 原版本：v0.2.1
        📥 更新包：live_monitor_v0.3.0.zip
        🗂 旧版备份：data/plugin_data/live_monitor/backup/v0.2.1-20261103-123020
        ────────────────────────
        ♻️ 5 秒后自动热重载，重载成功后本会话会再收到一条确认；没收到就去 WebUI → 插件管理 看原因，必要时用备份回滚。
（约 5 秒后，新版实例载入并在第一次轮询里回执）
插件:   ✅ 已更新到 v0.3.0 并完成热重载
        ────────────────────────
        📦 原版本：v0.2.1
        🗂 旧版备份：data/plugin_data/live_monitor/backup/v0.2.1-20261103-123020
        监控与订阅数据未受影响。
```

流程要点：

- **只有管理员能触发，且只在管理员明确下发指令时才动文件**。后台的版本检查不会自动更新，`self_update` 关掉后这条指令也会拒绝执行。
- 更新包优先取 Release 上本插件自己上传的 `live_monitor_v<版本>.zip`；没有就退回 GitHub 自动生成的源码包 `zipball_url`。下载体积硬上限 `MAX_UPDATE_BYTES = 2 MB`，响应头报超长就断、分块传输边读边断。
- 校验全部在内存里做完才允许落盘，任何一条不过就**一个字节都不写**：
  | 校验 | 不通过时的提示 |
  | --- | --- |
  | 必须是能打开的 zip | `更新包不是 zip 格式` / `更新包打不开: …` |
  | 条目路径不能是绝对路径、不能带 `..` | `更新包里有非法路径: …` |
  | `metadata.yaml` 只能在包根目录或单层目录下 | `更新包缺少 metadata.yaml` / `层级太深` |
  | 插件 `name` 必须还是 `live_monitor` | `更新包的插件名是 X，不是本插件 live_monitor` |
  | 版本必须比当前新 | `更新包版本 X 不比当前版本 Y 新` |
  | `main.py` 要能 `ast.parse`，且找得到以 `Plugin` 结尾的主类 | `语法不通过` / `找不到以 Plugin 结尾的主类，装上也不会被加载` |
  | `_conf_schema.json` 必须是合法 JSON | `不是合法 JSON: …` |
  | 只读白名单文件（`main.py`、`metadata.yaml`、`_conf_schema.json`，另有 `README.md`、`LICENSE` 可选） | 包里的其他条目一律不落盘 |
- **绝不删插件目录**：AstrBot 自带的更新器（`_PluginUpdater.update()`）是 `remove_dir(插件目录)` 再解压，一旦新版加载不起来，手工恢复很麻烦。本插件只覆盖白名单里的几个文件，其余内容（含 `logo.png` 之类）原样保留，备份目录里就是被覆盖前的原件。
- 备份放在 `data/plugin_data/live_monitor/backup/v<旧版本>-<时间戳>/`，只保留最近 **5** 份，更早的自动删。
- 热重载走 `context._star_manager.reload(<插件名>)`。AstrBot 没有给插件公开的重载接口，这是唯一能自己重载的办法，所以调用前做了两道确认：插件名先从 `context.get_all_stars()` 里找到本实例对应的 `StarMetadata.name`（找不到才退回 `metadata.yaml` 的 `name`），再用公开接口 `context.get_registered_star(name)` **确认这个名字确实注册过**——因为 `reload(name)` 匹配不到名字时会退化成重载**所有**插件，绝不能拿错名字去调。
- 重载排进独立任务（延迟 `RELOAD_DELAY = 5` 秒），因为 `reload()` 第一步就是终止当前实例；在指令协程里直接 `await` 会让本条指令的回复发不出去。
- 覆盖成功后先写标记文件 `data/plugin_data/live_monitor/update_pending.json`（记录 `from / to / umo / backup`），新版实例载入后在**第一次轮询**里对比自己的版本并回执，然后删除标记。回执只发给发起更新的那个会话，同样受 `notify_whitelist` 约束。
- 标记只在重载成功后删一次，不会反复回执；标记文件本身读坏了只记一行日志，不影响监控启动。
- 带版本号 `/直播监控 更新 0.3.1` 可以指定装哪个 tag（跳过"只要正式版"的限制，便于装还没转正式的版本）；但**热更新只往前装**：目标等于当前版本时回"当前已经是 vX，无需更新"，比当前旧时回"目标版本 X 比当前 vY 旧：热更新只往前装，回滚请用备份目录覆盖插件目录"，两种情况都不下载。回滚请用备份目录，或直接在 WebUI 里更新。

回滚与手工兜底：

```text
# 新版加载不起来（收到 ⚠️ 插件文件已覆盖，但没能载入新版本，或压根没收到回执）
1. AstrBot WebUI → 插件管理 → 直播监控 → 查看报错并重载一次
2. 仍然失败：把 data/plugin_data/live_monitor/backup/v<旧版本>-<时间戳>/ 里的文件
   覆盖回 data/plugins/live_monitor/，再重载插件
监控数据一直在 data/plugin_data/live_monitor/rooms.json，覆盖插件文件不会动它。
```

> 热更新依赖 `api.github.com` 与 Release 下载地址可达。机器直连 GitHub 不通时，可在 `update_asset_proxy` 填一个 `https://` 开头的镜像前缀（会拼在真实下载地址前面）；填 `http://` 会被拒绝——更新包等于要执行的代码，不能走明文。

## 配置项（WebUI 插件设置）

| 配置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `admin_ids` | string | 空 | 管理员用户ID（QQ号/Telegram ID 等），多个用逗号分隔；**留空则所有人可用**。仅管理员可执行 添加/删除/订阅/取消/监控UP/移除UP/订阅UP/退订UP/检查更新/更新 |
| `start_check_interval` | int | 30 | **开播检测间隔**（秒）：未开播的房间按此频率轮询，检测是否开播。最小生效 15 秒，过小可能被平台限流 |
| `end_check_interval` | int | 60 | **关播检测间隔**（秒）：正在直播中的房间按此频率轮询，检测是否关播 |
| `notify_start` | bool | true | 开播时是否推送 |
| `notify_end` | bool | true | 关播时是否推送 |
| `show_elapsed` | bool | true | **是否显示"距离上次"的时间**：开播通知里的「距离上次直播」与稿件通知里的「距上次更新」共用这一个开关。开启时按 `xx天`／不满一天 `xx小时` 显示；关掉后两处都不显示。取不到上一次时间时无论开关都会省略该行 |
| `upload_check_interval` | int | 300 | **UP 主稿件检查间隔**（秒）：只对已添加的 B站 UP 主生效，最小生效 60 秒。UP 主发稿频率低，没必要像开播那样高频查 |
| `notify_upload` | bool | true | UP 主发新稿件时是否推送。**关掉后仍会继续记录稿件基线**，重新打开不会把关掉期间的稿件补推送 |
| `upload_max_notify` | int | 3 | 一次检查最多推送几条新稿件的详情；超出则合并成一条列表消息（填 0 或非法值按默认 3 处理，最小按 1 生效） |
| `notify_whitelist` | text | 空 | **通知白名单**：仅这些会话UMO接收推送（开播/关播/稿件通知都算），多个用逗号分隔；留空则推送给所有订阅会话。格式如 `aiocqhttp:GroupMessage:123456789`、`telegram:GroupMessage:-100123`。管理员用 `列表` 指令可查看各会话的 UMO |
| `bilibili_cookie` | string | 空 | B站 Cookie（可选，直播接口或 UP 主稿件接口失败时再填）。**只会发给 `*.bilibili.com` / `*.bilibili.cn` / `*.hdslb.com`** 这几个B站自己的域名，其他站点的封面/接口请求一律不带，避免登录态外泄 |
| `update_check` | bool | true | 是否自动检查插件新版本（访问 `api.github.com`）。关掉后仍可用 `/直播监控 检查更新` 手动查 |
| `update_check_interval_hours` | int | 24 | 自动检查新版本的间隔（小时），最小生效 1 小时；填 0 或非法值按默认 24 处理 |
| `self_update` | bool | true | **是否允许 `/直播监控 更新` 下载并覆盖插件文件**。只影响这条由管理员手工触发的指令，后台版本检查绝不会自己更新；关掉后仍然可以 `检查更新` 查版本号再手工装 |
| `update_asset_proxy` | string | 空 | 下载更新包的镜像/加速**前缀**（可选，必须以 `https://` 开头，填 `http://` 会直接拒绝）。填了就把 GitHub 的下载地址拼在它后面，如 `https://mirror.example.com/https://github.com/…`；留空直连 |

> 三项间隔均可在 WebUI 插件设置中随时修改，修改后无需重启。
> 房间开播后自动切换到关播间隔，关播后切回开播间隔，兼顾响应速度与接口压力。

> 查询自己的用户ID：向机器人发送 `/sid`（AstrBot 内置指令）即可。

## 数据存储

监控列表（房间 + UP 主）保存在 `data/plugin_data/live_monitor/rooms.json`，可直接编辑/备份。**机器人重启、插件重载后监控与订阅均自动恢复**；恢复后首次检测只同步当前状态，不会重复推送通知。同一目录下还有热更新用到的两样东西：`update_pending.json`（一次更新的重载回执标记，回执发完就删）和 `backup/v<旧版本>-<时间戳>/`（覆盖前的原件，最多留 5 份）。结构（v4）：

```json
{
  "version": 4,
  "rooms": {
    "bilibili:123456": {
      "platform": "bilibili",
      "room_id": "123456",
      "title": "直播标题",
      "anchor": "主播昵称",
      "cover": "https://...封面图.jpg",
      "url": "https://live.bilibili.com/123456",
      "live": true,
      "last_live_at": 1762100000,
      "live_since": 1762088800,
      "watchers": { "aiocqhttp:GroupMessage:123456789": "群名片" }
    }
  },
  "ups": {
    "946974": {
      "mid": "946974",
      "platform": "bilibili",
      "name": "影视飓风",
      "face": "https://...头像.jpg",
      "archive_count": 951,
      "watchers": { "aiocqhttp:GroupMessage:123456789": "群名片" },
      "seen": ["BV1eee", "BV1ddd", "BV1ccc"]
    }
  }
}
```

`watchers` 的 key 是 AstrBot 的 `unified_msg_origin`（会话标识）；房间和 UP 主各自维护一份，所以某个群可以只订阅开播不订阅稿件，或反过来。`seen` 是该 UP 主已知的 BV 号，**从新到旧**保存，最多 `MAX_SEEN_UPLOADS = 60` 条，超出会丢弃最旧的——只影响对比窗口，不影响监控本身（只要 60 条窗口内出现新 BV 号就能发现）。`seen` 为空即代表还没建立基线，下一次检查只记录、不推送。`last_live_at` 是**最近一次看到这个房间在播的 unix 时间戳**（在播期间每轮刷新一次），开播通知里的「距离上次直播」就是它到当下的间隔；`0` 表示从没记过，此时那一行不显示。`live_since` 是**这一轮开播被抓到的时刻**（看到 `未开播 → 在播` 时写入、关播时清零），关播通知里的「⏱ 本次时长」= `last_live_at - live_since`；`0` 表示这轮的起点没抓到（升级前就在播、或添加时主播已经开着播），时长那一行省略。没人订阅的房间不会被轮询，所以 `取消` 指令取消掉最后一个订阅者、或载入时发现 `watchers` 为空，插件会把 `last_live_at` 与 `live_since` 一并清零——留着旧时刻，将来重新订阅就会显示一个误导性的「距离上次直播」和跨场的时长；`live` 不是 `true` 却带着 `live_since` 同样归零，否则下一场会减出一个假时长。

保存时先写同目录的 `rooms.json.tmp`、成功后再改名覆盖正式文件，正式文件要么是上一版的完整内容、要么是这一版的完整内容，不存在半个 JSON。

> **文件读坏了不会悄悄丢数据**：手工编辑写漏一个逗号时，插件日志会写 `读取监控数据失败: ...`，同时把这个文件**改名成 `rooms.json.bad-<时间戳>` 保留**并提示修好它再重载。因为改名而不是原地留着，下一次保存不会把一个空监控表覆盖到坏文件上（改名的动作，正是为了让旧内容还能手工恢复）。

> **旧数据自动升级**：
> - 0.1.1 及以前的 `rooms.json` 顶层直接就是房间表，插件载入时识别并读入；
> - 0.1.2 的 v2 结构里的 `submissions` / `reviewers`（群友投稿队列与审核会话）在 0.2.0 已无对应功能，载入时**直接丢弃**并写一行日志 `已忽略旧数据里的投稿队列（submissions/reviewers）…`，房间与订阅照常保留；
> - 0.2.0 的 v3 结构在 0.2.1 升到 v4，只是房间多了 `live_since` 一个字段：**v3 文件照常读**，缺这个字段按 `0` 处理（当前这场直播的关播通知不带时长，下一场起正常）；
> - 以上几种情况下次保存都会写成最新结构，不需要手工迁移。

手工编辑过这个文件也没关系：插件载入时会校验并修复，脏数据只会被丢弃而不会让轮询任务崩溃。

| 情况 | 处理 |
| --- | --- |
| 顶层不是对象 / 房间值不是对象 | 忽略该条并写日志 |
| `platform` 不在支持列表 | 跳过该房间 |
| 缺 `room_id` | 跳过该房间 |
| `room_id` 含该平台不允许的字符（`& ? / #`、路径、超长） | 跳过该房间并写日志：房间号会原样拼进请求 URL，不能让手工数据改写查询串 |
| 缺 `watchers`、或 `watchers` 不是对象 | 归一化成空对象（房间继续监控，只是没人订阅），`last_live_at` / `live_since` 一并归零 |
| 缺 `title / anchor / cover / url`、`live` 不是真假 | 补成空串 / `None`（`None` 表示首次检测只记录基线，不推送） |
| `room_id` 是数字 | 转成字符串，避免后续接口拼 URL 出错 |
| 缺 `last_live_at`、或它不是数字（老数据、手工填错） | 归零：第一次开播通知不带「距离上次直播」，之后照常 |
| 缺 `live_since`、不是数字，或 `live` 不是 `true` 却带着它（关播状态留着旧起点） | 归零：这一轮的关播通知不带「⏱ 本次时长」，下一轮开播重新记起点 |
| UP 主 key 不是纯数字 / 值不是对象 | 跳过该 UP 主并写日志 |
| UP 主缺 `name / face`、`archive_count` 不是数字 | 补成空串 / `0` |
| UP 主 `seen` 不是列表、含空项 | 逐项转字符串并去掉空值，超过 60 条截断 |
| `watchers` 里 key 为空 | 丢弃该条订阅 |

## 收不到稿件通知的排查

1. `/直播监控 列表` 看该 UP 主那行的 `已记录 N 条稿件` 还是 `待首次检测`。**一直是"待首次检测"**说明从没成功查过（网络、Cookie、mid 有误），日志里会有 `检查UP主 <mid> 失败(第N次): ...`。
2. 列表里 UP 主行首是 `-` 而不是 `√`，说明当前会话没订阅 → `/直播监控 订阅UP <mid 或 昵称>`。`监控UP` 只给**执行指令的那个会话**订阅，其他群要各自订阅。
3. 检查 `notify_whitelist` 是否漏了这个群的 UMO——稿件通知同样受白名单约束，被跳过的会话会写日志 `以下会话不在 notify_whitelist 内，跳过推送: [...]`。
4. 想把某个 UP 主从监控里彻底去掉，用 `移除UP`；`退订UP` 只是当前会话不再收，UP 主还在列表里。
5. 加完 UP 主后立刻发的那条提示里写了检查间隔（`稿件检查间隔 300 秒`），新稿件最多要等一个间隔才会推，不是没生效。
6. 日志里出现 `handle error: 'int' object has no attribute 'strip'` → 装的是 0.1.1 及以前的旧版。AstrBot 会把纯数字指令参数转成 `int`，旧版直接 `.strip()` 就崩了；0.1.2 起做了字符串兜底，0.2.0 覆盖 `添加/删除/订阅/取消/监控UP/移除UP/订阅UP/退订UP`，升级 `main.py` 即可。

## 收不到开播通知的排查

1. 管理员在**收不到通知的那个群**里执行 `/直播监控 列表`，管理员视角会列出每个房间的订阅 UMO。若没有该群的 `aiocqhttp:GroupMessage:群号`，说明这个群根本没订阅 → 执行 `/直播监控 订阅 平台:房间号`。
2. `添加 / 订阅 / 取消 / 删除` 默认是**管理员指令**：配置了 `admin_ids` 后，其他群里非管理员发这些指令会被拒绝（提示"该操作仅限管理员"），此时把该群群主的 QQ 号加进 `admin_ids`，或暂时留空。
3. 检查 `notify_whitelist` 是否只填了第一个群的 UMO。白名单会静默过滤其他群，被跳过的会话会写进日志：`以下会话不在 notify_whitelist 内，跳过推送: [...]`。
4. 日志里若出现 `推送通知到 xxx 失败`，`xxx` 的 UMO 就是没送到的会话：平台 ID 写错、该群已踢出机器人、或平台不支持主动消息（`qq_official`）都会在这里暴露。
5. 通知发得出去但没有「⏳ 距离上次直播」这一行 → 属预期：这个房间还没被记录过在播时刻（`rooms.json` 里 `last_live_at` 是 0，比如升级前的老数据、或添加后第一次开播），或 `show_elapsed` 被关掉了。下一次开播就会带上。
6. 关播通知没有「⏱ 本次时长」这一行 → 也是预期：这一轮的开播瞬间没被轮询抓到（`live_since` 是 0，常见于升级/添加插件时主播已经在播，或这中间房间被取消订阅过），下一场 `未开播 → 在播` 的完整轮次就会带上。有这一行但比实际短 1~2 分钟 → 正常，起点/终点都受轮询间隔限制，文案里的「约」就是这个意思。

## 热更新没成功的排查

1. 提示"该操作仅限管理员" → `更新` 是管理员指令，把自己的 ID 加进 `admin_ids`（或暂时留空）。
2. 提示 `self_update 已关闭` → 插件设置里 `self_update` 被关了，这是刻意的开关，打开才能覆盖文件。
3. `更新失败: ...`（HTTP 403 / 连不上 / 超时）→ GitHub 不可达。填 `update_asset_proxy`（必须 `https://` 开头）走镜像，或直接在 WebUI 的插件管理里更新。
4. `更新包校验未通过，已放弃覆盖：...` → **这是保护生效**，一个字节都没写。常见原因：Release 上的资产不是本插件的包（插件名不符）、tag 版本不比当前新、包结构不对。按提示里的原因处理，或改用 WebUI 更新。
5. 回复里有 `✅ 已下载 …` 但接着是 `⚠️ 自动热重载不可用` → 文件已经换成新版，只是这个 AstrBot 版本没把重载接口暴露给插件（或插件名没注册）。**去 WebUI → 插件管理重载一次**就生效，不要再发 `更新`（版本已经相同，会被"当前已经是 vX，无需更新"挡掉）。
6. 收到 `⚠️ 插件文件已覆盖，但没能载入新版本` → 新版 `main.py` 导入失败。日志里看 AstrBot 报的错，然后用 `data/plugin_data/live_monitor/backup/v<旧版本>-<时间戳>/` 里的文件覆盖回 `data/plugins/live_monitor/` 再重载即可回滚。
7. 什么回执都没收到 → 大概率是第 5、6 两种情况里重载阶段进程被终止后没能载入。`update_pending.json` 还留在那个会话的回执上，去 WebUI 手动重载一次插件，第一次轮询就会把结果补发出来。
8. 日志里有 `热重载失败: <原因>` → `reload()` 返回了错误（新版载入报错时 AstrBot 会把插件放进失败列表），按原因处理或回滚。

## 封面图与发送容错

开播通知与稿件通知都会附带封面。AstrBot 发送 http 图片链接时**每次发送都会重新拉一次图**，且不带防盗链 Referer、不校验状态码——多群广播时第 2 个群很容易拿到 403 错误页并抛异常，把整条通知（连文字一起）带走。因此本插件自己下载封面、转 base64 复用，并做了四道校验：

| 校验 | 不满足时的行为 |
| --- | --- |
| 封面地址必须是 `http(s)://` | 不发起下载 |
| HTTP 状态码必须是 200 | 放弃封面 |
| `Content-Type` 必须以 `image/` 开头 | 放弃封面（平台限流常返回 html） |
| 体积 ≤ `MAX_COVER_BYTES`（2 MB，响应头与正文各查一次） | 放弃封面 |

以上任一情况只记录 `封面下载失败，本次仅发送文字`，**文字通知照常发出**。带图消息在某个群发送失败时，还会对该群自动退回纯文字再发一次，保证通知不丢。多条稿件合并推送的那条消息不带封面（多个封面没有意义），只有单条详情通知配图。

## 已知限制

- **抖音**：无登录态时官方接口可能返回异常，插件会跳过该房间并记录日志，不影响其他房间。
- **虎牙/B站** 等接口均为非官方公开接口，平台改版后可能失效，届时需更新 `main.py` 中对应的 `check_*` / `fetch_up_*` 函数。
- **UP 主稿件只支持 B站**。
- **稿件列表每页只取最新 20 条**（`fetch_up_uploads(limit=20)`）。UP 主在一个检查间隔内发超过 20 条时会漏掉更早的几条——正常更新节奏不可能碰到，仅批量补档/搬运号需要注意。
- **B站空间接口有风控**：`x/space/wbi/arc/search` 需要 WBI 签名且频繁返回 `-352/-403`，本插件刻意不用它，改走免 WBI、免 Cookie 的 `x/v2/medialist/resource/list` + `x/web-interface/card`。若仍被限流，日志会写 `bilibili 稿件接口返回 code=-352（…）`，此时填 `bilibili_cookie` 或调大 `upload_check_interval`。
- 稿件对比靠 BV 号集合，**UP 主把旧稿件删除后又恢复、或改成同一 BV 不会重新通知**；改标题、换封面也不会（只认新 BV 号）。
- **「距离上次直播」是估算值**：取的是上一次轮询看到该房间还在播的时刻，比真实关播时刻晚不了多少，误差最多一个轮询间隔（默认 30/60 秒），不影响「x天/x小时」的读数。房间从没被观测到在播过（`last_live_at` 为 0）时该行不显示。
- **「本次时长」同样是估算值，而且是下限**：起点是轮询抓到的开播瞬间（最多比真实开播晚一个开播间隔），终点是最后一次看到在播的时刻（最多比真实关播早一个关播间隔），所以读数一般比实际少 1~2 个轮询间隔，文案里用「约」标明；跨天按 `x天x小时` 显示，分钟余数会被舍掉。插件没见过这轮开播（升级前就在播、或添加时已在播）时整行省略——不拿"我发现它"的时刻冒充开播时刻。
- **「距上次更新」依赖同一页里的上一条稿件**：接口按从新到旧返回，上一条就是它后面那条；如果只抓到一条（新号/被截断）或平台没给 `pubtime`，就没有参照，该行同样省略。
- 「距离上次」只出现在**开播通知**与**稿件通知**里，关播通知没有这个字段（关播的意义是结束，不是间隔）。
- `qqofficial`（QQ 官方 API 平台）不支持 AstrBot 主动消息，无法作为通知接收会话。
- B站直播通知中的"主播"字段在接口未返回昵称时显示 uid。
- 多群广播是**逐个发送、每个群之间间隔 1 秒**（防 QQ 频控）。订阅群数很多时，最后一个群会比第一个群晚几秒收到通知。
- **更新检查依赖 `api.github.com` 可达**：机器无法直连 GitHub（没配代理/被限流 403）时查不到新版本，插件只在日志里留一行 `检查插件更新失败: ...`，不影响监控。热更新的下载同理，不通就填 `update_asset_proxy` 走 https 镜像。
- **热更新只覆盖白名单文件**（`main.py`、`metadata.yaml`、`_conf_schema.json`、`README.md`、`LICENSE`），不会装依赖、也不会创建新目录：万一某个新版本引入了额外的 `.py` 文件或 `requirements.txt`，这条指令装不全，那种版本请用 AstrBot WebUI → 插件管理 更新（它会覆盖整个插件目录）。插件的更新包本来就只该有这几个文件，出现额外文件属于发布事故。
- **热更新靠 `context._star_manager` 这个非公开属性**：AstrBot 没给插件暴露重载接口，`reload(名字)` 匹配不到名字时会退化成重载所有插件，所以调用前一定先用公开接口 `get_registered_star()` 确认过名字注册过。若将来 AstrBot 改了这个内部属性，指令不会瞎调，而是回「自动热重载不可用（…），请到 WebUI 手动重载」——文件已经换好，手动重载一次即可。
- **没有无人值守的自动覆盖**：`update_check` 只负责提醒，`/直播监控 更新` 必须管理员亲手发；`self_update` 关掉后连这条指令也不动文件。让"从网上下载的代码自动跑在机器人里"这件事始终有一个人工确认环节。
