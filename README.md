# live-monitor 直播开播监控插件

基于 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 的直播状态监控插件：在聊天中自定义要监控的直播间，群友可**投稿**由管理员审核，自动检测开播/关播，并推送通知给订阅的群或个人。

## 功能特点

- 支持平台：**B站直播、斗鱼、虎牙、抖音直播**
- 聊天内指令管理监控列表，无需改配置文件
- 开播 / 关播自动推送通知，富文本模板包含**通知类型、主播名、平台、房间号、直播标题、直播间链接、直播封面图**
- 通知白名单（`notify_whitelist`）：按会话 UMO 精确控制哪些群/私聊实际接收推送
- **投稿投送**：群友用 `/直播监控 投稿 <直播间链接>` 投稿，插件先向平台校验房间确实存在（顺手取回主播、标题、是否在播），再把投稿**主动投送给审核会话**；管理员 `投稿通过` / `投稿拒绝` 处理，结果自动回投给投稿人
- **投稿防刷**：单会话最多 3 条待审、待审总数上限 50 条，重复投稿与已在监控中的房间会被直接挡掉
- 审核会话用 `/直播监控 审核订阅` 在群里自助登记（无需手填 UMO），`审核取消` 退出
- **支持热重载**：WebUI 重载/停用插件时自动保存数据、停止旧轮询任务；重复重载不会产生双任务并发推送；配置项（间隔、白名单、管理员等）修改即时生效，无需重启
- 管理员机制：可在配置中设置 `admin_ids`，仅管理员可添加/删除/订阅（留空则所有人可用）
- **开播/关播检测间隔分开自定义**：未开播房间高频轮询等开播，直播中房间低频轮询等关播，互不干扰
- 谁添加谁订阅，通知会推送给所有订阅的会话（群聊、私聊均可）
- **多群广播可靠投递**：封面图整次通知只下载一次并转 base64 复用（每群各发一条独立消息链，群与群之间间隔 1 秒），避免 AstrBot 每次发送都重新拉图被 CDN 防盗链拦截、导致除第一个群外整条通知丢失；带图发送失败会自动退回纯文字补发
- 监控与订阅数据持久化到磁盘，**机器人重启 / 插件重载后不丢失**，且重启后首次检测只记录状态、不刷屏
- 单个房间接口失败不影响其他房间监控（连续失败会写入日志）
- **插件自动检查新版本**：后台按间隔（默认 24 小时）查一次 GitHub Release，发现正式版新版本就把更新提醒投送给审核会话，同一版本只提醒一次；管理员也可随时用 `/直播监控 检查更新` 手动查

## 安装

1. 下载本仓库，或下载 Release 页的 `live_monitor_v<版本>.zip`
2. 把 `main.py`、`metadata.yaml`、`_conf_schema.json` 放进 AstrBot 的 `data/plugins/live_monitor/`（目录名用 `metadata.yaml` 里的 `name`，AstrBot 按它生成模块路径 `data.plugins.live_monitor.main`）：

   ```
   data/plugins/live_monitor/
   ├── main.py
   ├── metadata.yaml
   └── _conf_schema.json
   ```

3. 在 AstrBot WebUI「插件管理」中重载插件并启用即可。

> 从旧版本升级只需覆盖 `main.py`（`metadata.yaml`、`_conf_schema.json` 有新增配置项时一并覆盖）；监控数据在 `data/plugin_data/live_monitor/rooms.json`，不会被更新动到。

> 依赖 `aiohttp`，AstrBot 已内置，无需额外安装。
>
> 命名与规范注意（依据官方开发文档 <https://docs.astrbot.app/dev/star/plugin-new.html> 与 AstrBot 源码）：
> - `metadata.yaml` 的 `name` 必须是合法 Python 标识符（下划线，不能含 `-`），本插件为 `live_monitor`；
> - 插件主类名必须以 `Plugin` 结尾（本插件为 `LiveMonitorPlugin`），否则 AstrBot 扫描不到；
> - `astrbot_version` 使用 PEP 440 范围且不加 `v` 前缀；
> - 代码用 `ruff format` 格式化；依赖用 `aiohttp`（AstrBot 已内置 `aiohttp>=3.11.18`，因此本插件不提供 `requirements.txt`，避免重载时多余的 pip 步骤）；
> - **插件类里不要定义 `__del__`**：AstrBot 的 `_terminate_plugin()` 是 `if "__del__" ... elif "terminate" ...`，一旦有了 `__del__`，`terminate()` 就不会被调用，后台轮询任务不会被取消，重载后会出现双任务并发推送。

## 使用方法

指令前缀：`/直播监控`（别名 `/开播监控`）

| 指令 | 说明 | 权限 |
| --- | --- | --- |
| `/直播监控 添加 <直播间链接>` | 添加监控并订阅本会话通知 | 管理员 |
| `/直播监控 添加 <平台:房间号>` | 同上，手动指定平台 | 管理员 |
| `/直播监控 列表` | 查看监控列表与当前状态 | 所有人 |
| `/直播监控 订阅 <平台:房间号>` | 本会话订阅某个已监控房间 | 管理员 |
| `/直播监控 取消 <平台:房间号>` | 取消本会话订阅（不删除监控） | 管理员 |
| `/直播监控 删除 <平台:房间号>` | 删除整个监控 | 管理员 |
| `/直播监控 投稿 <直播间链接>` | 投稿房间，投送给管理员审核 | 所有人 |
| `/直播监控 投稿列表` | 查看待审核投稿及编号 | 管理员 |
| `/直播监控 投稿通过 <编号>` | 通过投稿，房间加入监控并给投稿人订阅 | 管理员 |
| `/直播监控 投稿拒绝 <编号> [原因]` | 拒绝投稿并回投投稿人（原因不能含空格） | 管理员 |
| `/直播监控 审核订阅` | 让本会话接收投稿推送 | 管理员 |
| `/直播监控 审核取消` | 本会话不再接收投稿推送 | 管理员 |
| `/直播监控 检查更新` | 立即查一次 GitHub 上有没有新版插件 | 管理员 |
| `/直播监控 帮助` | 查看帮助 | 所有人 |

> 配置了 `admin_ids` 后，非管理员执行受限指令会提示"该操作仅限管理员"。
>
> `投稿` 是**唯一对所有用户开放**的管理类指令：它不会直接改监控列表，只产生一条待审核投稿。

### 投稿与审核流程

```text
群友:  /直播监控 投稿 https://live.bilibili.com/6
插件:  （调平台接口校验房间存在，取回主播/标题/在播状态）
插件:  → 投送给所有「审核订阅」过的会话（每个会话间隔 1 秒）
插件:  ← 回复群友 "已投稿（#1），并投送给 2 个审核会话"
管理员: /直播监控 投稿通过 1
插件:  → 房间加入监控表，投稿人会话 + 当前审核会话自动订阅
插件:  ← 回投投稿人 "✅ 投稿 #1 已通过审核"
```

审核会话收到的推送长这样：

```text
📮 新投稿 #1 待审核
────────────────
👤 主播：哔哩哔哩英雄联盟赛事
📡 平台：B站直播
🚪 房间：6
📺 标题：今天和大家聊聊新版本
📊 状态：直播中
🙋 投稿人：某群友
🔗 https://live.bilibili.com/6
────────────────
/直播监控 投稿通过 1
/直播监控 投稿拒绝 1 [原因]
```

要点：

- **审核会话靠 `审核订阅` 指令登记，不靠配置文件**。在哪个群执行 `审核订阅`，投稿就投送到哪个群；没登记任何审核会话时，投稿仍会排队保存，只是不会主动推送，管理员可用 `投稿列表` 手动查看（插件会在回复里明确提示"还没有审核会话"，不会假装已推送）。
- `投稿通过` 只影响监控与订阅，不会重新下载封面；新房间首次检测只记录状态，不刷屏。
- 房间已在监控列表 / 已有相同待审投稿 / 本人待审满 3 条 / 全局待审满 50 条，四种情况都会被挡回并说明原因。
- 若房间此前被管理员直接 `添加` 过，`投稿通过` 只追加订阅，不重置监控状态。

### 支持的添加方式示例

```text
/直播监控 添加 https://live.bilibili.com/123456        B站直播间链接
/直播监控 添加 https://space.bilibili.com/946974       B站主播主页（自动解析房间号）
/直播监控 添加 https://www.douyu.com/85894             斗鱼链接
/直播监控 添加 https://www.huya.com/房间号              虎牙链接
/直播监控 添加 https://live.douyin.com/742060668528    抖音链接
/直播监控 添加 bili:123456                             平台前缀写法
/直播监控 添加 斗鱼:85894                               中文前缀亦可（b站/斗鱼/虎牙/抖音）
```

`投稿` 接受与 `添加` 完全相同的房间写法（链接、`平台:房间号`、纯数字、B站主播主页链接均可）。

## 插件自动更新检查

插件会自己查有没有新版本，但**只提醒、不自动覆盖文件**——真正的更新动作仍然由 AstrBot 的插件管理器执行，避免插件自己改自己的目录。

- 版本号只写在 `metadata.yaml` 里一份，插件启动时读它，同时从 `repo` 字段解析出仓库地址（本插件是 `qzuser/live-monitor`）。
- 启动 60 秒后做第一次检查（避开插件加载阶段主动消息通道还没就绪），之后每 `update_check_interval_hours` 小时查一次，复用原来那一个轮询任务，不会新增后台任务。
- 查的是 `https://api.github.com/repos/<仓库>/releases`，并且**跳过 draft、prerelease 以及 tag 名带 alpha/beta/rc/dev 的版本**——口径和 AstrBot 自带更新器一致，防止提醒你的版本在 WebUI 里根本点不了更新。
- 发现新版本 → 投送给所有 `审核订阅` 过的会话，并把提醒过的版本号记下来，**同一个版本只提醒一次**（重启/热重载后会重新提醒一次）。
- 一个审核会话都没有时不静默丢弃，日志里会写"没有审核会话可提醒，管理员请用 /直播监控 检查更新 查看"。

提醒长这样：

```text
🆕 直播监控插件可更新
────────────────
📦 当前版本：v0.1.2
✨ 最新版本：v0.2.0
🗓 发布于：2026-10-10
🔗 https://github.com/qzuser/live-monitor/releases
────────────────
- 新增投稿审核
- 修复纯数字房间号崩溃
────────────────
更新方式：AstrBot WebUI → 插件管理 → 本插件 → 更新（由 AstrBot 覆盖插件目录，监控数据在 data/plugin_data 下不受影响）
```

`/直播监控 检查更新` 是同一套逻辑的手动入口：没新版本时回"当前 vX 已是最新版本（仓库最新正式版：vY）"，仓库上一个正式版 Release 都没发时回"… 上还没有正式版 Release，无法比较版本"，请求失败时回"检查更新失败: <原因>"。手动查过的版本同样会被标记，后台不会再推第二遍。

> 连不上 GitHub（网络被墙、限流 403、离线）只记一条 `检查插件更新失败: ...` 日志，**不会中断开播轮询**。彻底不想让插件联网查版本，把 `update_check` 关掉即可，之后仍然可以手动 `检查更新`。

## 配置项（WebUI 插件设置）

| 配置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `admin_ids` | string | 空 | 管理员用户ID（QQ号/Telegram ID 等），多个用逗号分隔；**留空则所有人可用**。仅管理员可执行 添加/删除/订阅/取消/投稿列表/投稿通过/投稿拒绝/审核订阅/审核取消/检查更新 |
| `start_check_interval` | int | 30 | **开播检测间隔**（秒）：未开播的房间按此频率轮询，检测是否开播。最小生效 15 秒，过小可能被平台限流 |
| `end_check_interval` | int | 60 | **关播检测间隔**（秒）：正在直播中的房间按此频率轮询，检测是否关播 |
| `notify_start` | bool | true | 开播时是否推送 |
| `notify_end` | bool | true | 关播时是否推送 |
| `notify_whitelist` | text | 空 | **开播/关播通知白名单**：仅这些会话UMO接收推送，多个用逗号分隔；留空则推送给所有订阅会话。格式如 `aiocqhttp:GroupMessage:123456789`、`telegram:GroupMessage:-100123`。管理员用 `列表` 指令可查看各房间订阅会话的 UMO |
| `bilibili_cookie` | string | 空 | B站 Cookie（可选，接口失败时再填） |
| `update_check` | bool | true | 是否自动检查插件新版本（访问 `api.github.com`）。关掉后仍可用 `/直播监控 检查更新` 手动查 |
| `update_check_interval_hours` | int | 24 | 自动检查新版本的间隔（小时），最小生效 1 小时；填 0 或非法值按默认 24 处理 |

> **投稿推送不受 `notify_whitelist` 约束**：白名单只管开播/关播通知；投稿发给谁，由 `审核订阅` 指令登记的会话决定。这样管理员不必为了收投稿而去改配置。

> 两项间隔均可在 WebUI 插件设置中随时修改，最小生效值 15 秒；修改后无需重启。
> 房间开播后自动切换到关播间隔，关播后切回开播间隔，兼顾响应速度与接口压力。

> 查询自己的用户ID：向机器人发送 `/sid`（AstrBot 内置指令）即可。

## 数据存储

监控列表、待审核投稿与审核会话保存在 `data/plugin_data/live_monitor/rooms.json`，可直接编辑/备份。**机器人重启、插件重载后监控、订阅、待审投稿、审核会话均自动恢复**；恢复后首次检测只同步当前状态，不会重复推送通知。结构（v2）：

```json
{
  "version": 2,
  "rooms": {
    "bilibili:123456": {
      "platform": "bilibili",
      "room_id": "123456",
      "title": "直播标题",
      "anchor": "主播昵称",
      "cover": "https://...封面图.jpg",
      "url": "https://live.bilibili.com/123456",
      "live": true,
      "watchers": { "aiocqhttp:GroupMessage:123456789": "群名片" }
    }
  },
  "submissions": {
    "1": {
      "platform": "bilibili",
      "room_id": "6",
      "title": "直播标题",
      "anchor": "主播昵称",
      "url": "https://live.bilibili.com/6",
      "live": true,
      "submitter_umo": "aiocqhttp:GroupMessage:2002",
      "submitter_name": "投稿人昵称",
      "created_at": 1762500000.0
    }
  },
  "reviewers": { "aiocqhttp:GroupMessage:1001": "管理群名片" }
}
```

`watchers` / `reviewers` 的 key 是 AstrBot 的 `unified_msg_origin`（会话标识）：`watchers` 收开播/关播推送，`reviewers` 收新投稿推送。投稿编号只在待审队列内有意义，通过或拒绝后该条即从 `submissions` 移除；重启后编号从"现存最大编号 + 1"继续，不会撞号。

> **旧数据自动升级**：0.1.1 及以前的 `rooms.json` 顶层直接就是房间表，插件载入时会识别并读入，下次保存自动写成 v2 结构，不需要手工迁移。

手工编辑过这个文件也没关系：插件载入时会校验并修复，脏数据只会被丢弃而不会让轮询任务崩溃。

| 情况 | 处理 |
| --- | --- |
| 顶层不是对象 / 房间值不是对象 | 忽略该条并写日志 |
| `platform` 不在支持列表 | 跳过该房间 / 该投稿 |
| 缺 `room_id` | 跳过该房间 / 该投稿 |
| 缺 `watchers`、或 `watchers` 不是对象 | 归一化成空对象（房间继续监控，只是没人订阅） |
| 缺 `title / anchor / cover / url`、`live` 不是真假 | 补成空串 / `None`（`None` 表示首次检测只记录基线，不推送） |
| `room_id` 是数字 | 转成字符串，避免后续接口拼 URL 出错 |
| 投稿编号不是数字、缺 `submitter_umo` | 丢弃该投稿（没投稿人就没人能收审核结果） |
| 投稿 `created_at` 不是数字 | 归一化成 `0`，列表里显示"时间未知" |
| 审核会话 key 为空 | 丢弃该条 |

## 投稿收不到 / 处理不了的排查

1. 投稿后回复里写的是"目前还没有审核会话接收投稿" → 从没执行过 `审核订阅`，或执行它的人不是管理员（配了 `admin_ids` 时非管理员会被拒）。在希望接收投稿的群里由管理员执行 `/直播监控 审核订阅`。
2. 回复里写"推送给 N 个审核会话均失败" → 审核会话登记了但主动消息发不出去，日志里会是 `推送通知到 <UMO> 失败: ...`；"并投送给 N 个审核会话"的 N 比登记的少，也是同一类问题，按上一节排查（`qq_official` 不支持主动消息）。
3. 管理员想处理积压但不记得编号 → `/直播监控 投稿列表`；`/直播监控 列表` 的管理员视角也会在末尾提示还有几条待审。
4. 投稿通过了但群里没收到开播通知 → 通过时订阅的是**投稿人会话**和**审核者会话**，其他群需要各自 `订阅`。
5. 日志里出现 `cmd_sub / cmd_del handle error: 'int' object has no attribute 'strip'` → 装的是 0.1.1 及以前的旧版。AstrBot 会把纯数字指令参数转成 `int`，旧版 `parse_room_input` / `_resolve_key` 直接 `.strip()` 就崩了；0.1.2 起做了字符串兜底，覆盖 `添加/删除/订阅/取消/投稿/投稿通过/投稿拒绝`，升级 `main.py` 即可。

## 封面图与发送容错

开播通知会附带直播封面。AstrBot 发送 http 图片链接时**每次发送都会重新拉一次图**，且不带防盗链 Referer、不校验状态码——多群广播时第 2 个群很容易拿到 403 错误页并抛异常，把整条通知（连文字一起）带走。因此本插件自己下载封面、转 base64 复用，并做了四道校验：

| 校验 | 不满足时的行为 |
| --- | --- |
| 封面地址必须是 `http(s)://` | 不发起下载 |
| HTTP 状态码必须是 200 | 放弃封面 |
| `Content-Type` 必须以 `image/` 开头 | 放弃封面（平台限流常返回 html） |
| 体积 ≤ `MAX_COVER_BYTES`（2 MB，响应头与正文各查一次） | 放弃封面 |

以上任一情况只记录 `封面下载失败，本次仅发送文字`，**文字通知照常发出**。带图消息在某个群发送失败时，还会对该群自动退回纯文字再发一次，保证通知不丢。

## 多群收不到通知的排查

1. 管理员在**收不到通知的那个群**里执行 `/直播监控 列表`，管理员视角会列出每个房间的订阅 UMO。若没有该群的 `aiocqhttp:GroupMessage:群号`，说明这个群根本没订阅 → 执行 `/直播监控 订阅 平台:房间号`。
2. `添加 / 订阅 / 取消 / 删除` 默认是**管理员指令**：配置了 `admin_ids` 后，其他群里非管理员发这些指令会被拒绝（提示"该操作仅限管理员"），此时把该群群主的 QQ 号加进 `admin_ids`，或暂时留空。
3. 检查 `notify_whitelist` 是否只填了第一个群的 UMO。白名单会静默过滤其他群，0.1.1 起被跳过的会话会写进日志：`以下会话不在 notify_whitelist 内，跳过推送: [...]`。
4. 日志里若出现 `推送通知到 xxx 失败`，`xxx` 的 UMO 就是没送到的会话：平台 ID 写错、该群已踢出机器人、或平台不支持主动消息（`qq_official`）都会在这里暴露。

## 已知限制

- **抖音**：无登录态时官方接口可能返回异常，插件会跳过该房间并记录日志，不影响其他房间。
- **虎牙/B站** 等接口均为非官方公开接口，平台改版后可能失效，届时需更新 `main.py` 中对应的 `check_*` 函数。
- `qqofficial`（QQ 官方 API 平台）不支持 AstrBot 主动消息，无法作为通知接收会话。
- B站通知中的“主播”字段在接口未返回昵称时显示 uid。
- 多群广播是**逐个发送、每个群之间间隔 1 秒**（防 QQ 频控）。订阅群数很多时，最后一个群会比第一个群晚几秒收到通知。
- **投稿的"原因"参数不能含空格**：AstrBot 按空格切分指令参数，`投稿拒绝 1 与已有房间重复` 只有"与已有房间重复"会被记入原因，后面的词会被丢掉。想写长说明请拒绝后单独在群里解释，或用 `_` 连字符代替空格。
- 投稿只登记房间，**不会同时下载封面**；封面在首次轮询时随房间信息一起补齐。
- 投稿校验会实际调用一次平台接口，平台限流时校验也会失败，此时提示"直播间校验失败"，稍后再试即可。
- **更新检查依赖 `api.github.com` 可达**：机器无法直连 GitHub（没配代理/被限流 403）时查不到新版本，插件只在日志里留一行 `检查插件更新失败: ...`，不影响开播监控。
- 更新提醒**只负责告诉你有新版本**，不会自己下载覆盖。用 AstrBot WebUI 的插件管理更新最稳（它会覆盖整个插件目录，手工改过的 `main.py` 会被替换，监控数据在 `data/plugin_data/` 下不受影响）。

## 开发与许可

```bash
python tests/run.py                # 两套一起跑
python tests/test_submission.py    # 投稿投送
python tests/test_update_check.py  # 更新检查
```

投稿套覆盖旧数据升级、投稿→投送→通过/拒绝、查重与防刷上限、纯数字参数（`订阅/取消/删除/投稿通过` 全部按 int 传一遍）、脏数据清理、原有开播推送路径不受影响；更新检查套覆盖版本号比较、跳过预发布 Release、同一版本只提醒一次、`update_check` 开关、检查失败不影响轮询。共 24 项用例。
